# SOLID: шпаргалка к защите (вариант 8)

Код первой работы (`14_09/Practice.py`) переписан по принципам SOLID в `Practice.py`.
Запуск программы: `python Practice.py`. Запуск тестов: `python -m unittest -v`.

данные — только хранят их.

## Повторное использование: общие базовые классы

Общая логика вынесена в базовые классы, наследники её не дублируют.

```
Validator                 название поля, единый текст ошибки «поле «X» ...»
├── NamePartValidator
└── RangeValidator        проверка отрезка [minimum, maximum]
    ├── IntRangeValidator
    └── FloatRangeValidator

RetryingReader            цикл повторного ввода
├── TextReader            наследник задаёт только convert()
├── IntReader
└── FloatReader
```

Вспомогательные методы базовых классов (`error`, `is_in_range`, `range_reason`,
`read_value`) помечены `@protected` из `accessify`: снаружи их не вызвать, наследникам можно.
Одноразовый разбор строки в `IntReader` и `FloatReader` (`parse`) помечен `@private`.

Базовые классы — это не интерфейсы: в них есть логика. Интерфейсы (`I...`) по-прежнему
содержат только абстрактные методы, а рабочий класс наследует и базовый класс, и интерфейс:
`IntRangeValidator(RangeValidator, IIntValidator)`.

## O: открыт для расширения, закрыт для изменения

Нет `if/elif` по типу студента. Тип выбирается по словарю `creators`, форматировщик —
по словарю в `StudentFormatterByType`.

Если появится новый тип, например «автомат за проект», нужно:

1. написать класс `ProjectStudent(AutomaticStudent)`;
2. написать `ProjectStudentCreator` и `ProjectStudentFormatter`;
3. добавить по строке в словари в `ApplicationBuilder`.

Ни один существующий рабочий класс при этом не меняется.

## L: подстановка Лисков

`ExamStudent`, `OlympiadStudent` и `ControlWorkStudent` работают везде, где ожидается
`Student`: в хранилище, фильтре, принтере. Наследники не меняют смысл свойств
родителя и не бросают неожиданных исключений.

## I: узкие интерфейсы

- Хранилище реализует два интерфейса: `IStudentReceiver` (только `add`) и
  `IStudentProvider` (только `get_all`). Сценарий ввода получает только `IStudentReceiver`,
  `Task` — только `IStudentProvider`.
- Создатель студента с экзаменом получает `IIntReader`, а не весь ввод.
- Фильтр получает `IStudentChecker` с одним методом `check`.

## D: зависимость от абстракций

- Интерфейсы — абстрактные классы без свойств, только с `@abstractmethod`
  (`IInput`, `IOutput`, `ITextValidator`, …).
- Почти каждый рабочий класс реализует интерфейс, а `StudentRepository` — сразу два
  (множественное наследование).
- Зависимости передаются в конструктор как интерфейсы. Конкретные классы создаются
  только в `ApplicationBuilder`.

**Почему «инверсия».** Без принципа D зависимость идёт сверху вниз: `Task` напрямую
зависит от `StudentRepository`, а сценарий ввода — от `input()`. С принципом D интерфейс
описывает то, что нужно верхнему уровню (`IStudentProvider`, `IInput`), и нижний уровень
подстраивается под него, реализуя этот интерфейс. Стрелка зависимости у нижнего уровня
развернулась: теперь он зависит от абстракции, а не верхний от него. Поэтому в тестах
`ConsoleInput` легко заменить на `MockInput`.

## Отзывчивый CLI

- При ошибке переспрашивается только неверное поле, а не весь студент.
- Регистр и лишние пробелы не учитываются, первая буква ФИО делается заглавной.
- Дробные числа принимаются и с точкой, и с запятой.
- Есть меню типов, сообщения об успешном добавлении, итог ввода и нумерованный вывод.

## Тесты и mock-объекты

`test_practice.py` — 73 теста, каждый класс проверяется отдельно.
Вместо `input()` и `print()` подставляются `MockInput` и `MockOutput`, которые реализуют
те же интерфейсы `IInput` и `IOutput`. Остальные зависимости заменяются заглушками
(`StubIntReader`, `MockReceiver`, `StubChecker`, …), чтобы тестировать класс отдельно
от остальных.
